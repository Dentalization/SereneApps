# Dental multi-view reconstruction engineering walkthrough

**2026-09-25.** This records the current uncommitted implementation and its limits. The first live capture evidence remains the 15.3 s, 1080 × 1920 video: 18 selected frames, 86 points, 94 triangles, all 86 projected points outside the visible teeth, and seven registered cameras that did not contribute to the best-pair mesh. Those are findings about that capture, not a validation cohort. See [the capture audit](FIRST_CAPTURE_GEOMETRY_AUDIT.md).

The second inspected capture (30.93 s, 1080 × 1920) has a different primary input failure: inspected source frames show a **monitor displaying a dental graphic**, with bezel, cursor and screen artifacts, rather than physical teeth or a physical cast. Its stored LIDRA v3 report selected 24 frames globally. The reconstruction used a best pair, registered only two views, and generated a 34-vertex/17-face diagnostic mesh with no dense multiview result. Reprocessing the unchanged original video through LIDRA v4 in a temporary directory flagged a suspected display border in 23 of 24 analyzed frames and returned `CAPTURE_TARGET_SCREEN_SUSPECTED`. This is a conservative heuristic and review trigger, not a validated screen classifier. The original scan artifacts were not overwritten; historical v3 status will not retroactively gain the new reason. These are failure-investigation observations, **not** reconstruction or clinical validation results.

## Exact executed path

`DentistScan3DScreen.jsx` records video → `scan3DService.js` uploads it → Node inspects and stores the original video/hash → `scan3DWorker.js` launches an isolated attempt → `lidraService.js` calls Python `lidra_service.py` → `pythonServiceEngine.js` calls `reconstruction_service.py` → Node verifies asset hashes and evaluates `scanGeometryQuality.js` → X-Core can show a failed attempt's diagnostic mesh, while only a candidate can be published as an experimental visualization asset.

The engine registry name is still `opencv_sparse_sfm` for compatibility. The executed Python implementation is **OpenCV SIFT + ratio matching + fundamental/essential matrix RANSAC + best-pair initialization + PnP registration + three-or-more-view track triangulation + local PyTorch CPU bundle adjustment (or retention of an already low-error initial solution) + OpenCV rectified StereoSGBM + two-pair/three-view voxel support + a union of supported depth-map patches**. Its current version is `2.5.0`. No COLMAP, OpenMVS, Neuralangelo, DUSt3R, MASt3R, MUSt3R, ABot-Recon or TeethDreamer code is silently substituted or executed. COLMAP/OpenMVS executables are absent from this environment, so that separate baseline is not claimed.

If sparse SfM, bundle adjustment or dense stereo cannot meet evidence thresholds, the OBJ/STL remains a **best-pair sparse diagnostic**, not a dental scan. The PLY can contain measured three-view sparse tracks, but that does not make the mesh dense. The Python report and Node quality gate preserve this distinction. Scale remains arbitrary; no camera calibration certificate or physical reference is present.

## Changes from the audited baseline

| Stage | Before | Current implementation |
| --- | --- | --- |
| Acquisition | Uniform frames and whole-image quality could accept chin/clothing features. | Uniform sampling can still produce a **global diagnostic mesh**, but can never pass the dental quality gate. Operator-annotated, video-SHA-bound dental polygons permit ROI sharpness, luminance, glare, features, geometric overlap, displacement proxy, declared mouth stability and declared region coverage to be measured per frame. Rejected frames carry reasons. Annotation and tooth identity are **operator-declared and unverified**, not authenticated clinician findings. LIDRA v4 also records a persistent dark-border screen suspicion on each analyzed frame and prevents such captures from being called dental-ready; absence of that cue does not prove a physical target. |
| Keyframes | Uniform subsampling into the SfM frame budget. | Accepted frames are selected deterministically for declared region gain, temporal diversity, image-displacement and feature-count proxies. Physical translation is not measured by this heuristic. |
| Camera | Focal length approximated from frame dimensions; lens not pinned. | Supplied intrinsics/distortion are accepted and recorded as uncertified; unknown calibration is recorded. The mobile requests zero zoom and the wide-angle lens on iOS. Android physical lens identity remains unavailable. Both remain unvalidated for metric scale. |
| Sparse geometry | Best pair produced all points/mesh; extra poses did not add geometry. | Dental-mask-limited SIFT matches, geometric pair verification, three-view tracks, reprojection and parallax filtering, and an attempted joint pose/point optimization produce separately reported sparse evidence. Initialization is still best-pair and optimization can be rejected. |
| Dense geometry | No dense stage. | CPU StereoSGBM runs on registered pairs. Pair budget now prioritizes overlapping temporal neighbors across the **entire** sweep before wider baselines, so the right edge is not silently omitted at eight views and twelve pairs. Attempted and successful frame pairs are reported separately. Only depth pixels whose voxel has at least two pair estimates spanning three views form the dense candidate surface. Supported patches from more than one pair are retained where they add previously uncovered voxels; no triangles bridge unobserved gaps. Per-vertex view bitsets, pair counts, and per-face source-pair IDs are saved in `vertex_support.npz` with a SHA-256 digest. This is a conservative experimental baseline, not proven dental MVS. |
| Tooth and mesh audit | Face/vertex counts could pass for the wrong object. | Optional operator-declared tooth polygons yield projected observed-patch counts and source frames, explicitly without anatomical completeness or verified FDI identity. Mesh report includes components, boundary/nonmanifold/winding/duplicate counts and a bounded VTK self-intersection audit. Node checks the support-artifact hash, three-view dense support, per-tooth observed patches, bundle adjustment and topology before publishing a **candidate visualization**. |
| Provenance | Video/asset checksums and attempt metadata. | Adds mask annotation digest, selected/rejected frame reasons, geometry and support metrics, camera poses, source-code hashes, dense support artifact checksum, topology and processing timings. A rejected mesh remains available as a diagnostic, not as a ready scan. |

For the common one-arch phone workflow, the mobile guide now suggests a brief left → front → right sweep with an additional occlusal angle only where needed. This timing is a **prompt**, not a measured readiness threshold. The failed-scan screen and X-Core diagnostic viewer show the likely primary cause and view/mesh counts; the long list of downstream quality codes remains available on demand. When the screen-suspicion reason is present, the mobile recommends directly recording physical teeth or a physical cast. If a historical status has only the generic code, the mobile does not prescribe another recording or retry without a stage-specific reason. The public report recognizes LIDRA v2–v4, and the quality gate is v4. The app still lacks integrated per-frame ROI review or validated automatic tooth segmentation, so a quick unaudited phone video remains diagnostic-only.

The **Full Arch** selector is now enabled as a paired capture workflow: one short upper-arch video is uploaded/queued, then the dentist can start a separate lower-arch video without selecting the patient again. The two scan IDs share a server-verified pair group after the upper video is stored; the backend verifies patient, dentist, upper role, and presence of an uploaded upper video before creating the lower session. Each scan has its own reconstruction status and diagnostic assets. This is not a fused upper/lower mesh or verified full-arch anatomy. Closing the mobile screen before starting the lower recording currently loses the in-memory continuation action, although the existing upper scan remains in X-Core.

## How to exercise the research path

1. Preserve the original uploaded video. From `backend/python_service`, run `../../.venv/bin/python -m research.dental_roi_prepare --video /absolute/path/to/video.mp4 --output /private/review-directory`. This writes private preview JPEGs, a self-contained offline `annotate.html`, and an **incomplete** `roi_template.json`; it does not invent or approve regions.
2. Open the private `annotate.html` locally. A human reviews each preview, clicks a polygon tightly enclosing only visible teeth, explicitly accepts the frame, records `mouthStable` and `visibleRegions`, and enters a reviewer label and intended `expectedRegions`. Optional FDI tooth polygons are operator labels only. Export the reviewed JSON; the exact original video's SHA-256 embedded in it must match the uploaded bytes. Do not use a full-frame polygon to make the pipeline pass.
3. Submit the completed object as `configuration.frameSampling.dentalRegions` with `strategy: "geometry_aware"` when queueing the uploaded scan. The [experiment schema](experiment.schema.json) defines the fields. The existing mobile screen does **not** yet provide the per-frame annotation interface. Its one-tap queue flow may produce a global **diagnostic-only** mesh when ordinary SfM works, but it cannot become a dental candidate. This is an open end-to-end product gap, not a reconstruction success.
4. Inspect `lidra_analysis.json`, `reconstruction_report.json`, `vertex_support.npz` when dense reconstruction executes, and the Node `qualityAssessment`/private provenance. A `candidate` means only that engineering evidence floors passed. It does not mean every tooth, full arch, experimental accuracy or clinical accuracy.

## Controlled software verification and limits

The deterministic **planar software fixture** with three translated views, 240 × 320 images and arbitrary camera units executed three stereo pairs, produced 16,560 raw stereo samples, 607 three-view supported voxels, 5,520 supported vertices and 10,744 faces; its local CPU dense-stage time was about 314 ms on this host in one run. A four-view, partial-mask fixture retained two source-pair patches covering 660 supported voxels, with 5,674 vertices, 10,887 faces, two disconnected components, no nonmanifold edges and no detected self-intersections. Every returned vertex had at least three view bits and two pair estimates. These numbers test code execution and provenance only. They are **not dental reconstruction results or validation metrics**. A two-view input returned `insufficient_registered_views`.

The separate synthetic feature-video test exercises acquisition, multi-view sparse tracks, registered poses, output checksums, deterministic replay, rejection of tampered frames and arbitrary-scale labeling. It does not measure a patient or reference surface. The real capture has not been rerun through the new ROI path because no actual reviewed dental annotations are available. There is therefore no honest before/after patient geometry count.

Reproduce the software checks from the repository root with `./.venv/bin/python -m unittest backend.python_service.tests.test_scan3d_research -q` and `node --test backend/tests/scan3d.integrity.test.js`. Validation inputs in [the research runbook](README.md) stay `DATASET_UNAVAILABLE` until actual paired repeat videos and independent STL/PLY references are supplied. DICOM research files are likewise unavailable.

## Remaining blockers and failure modes

The largest blocker is **reliable dental-region evidence in the real phone workflow**: there is no integrated per-frame annotation or validated automatic segmentation, and the first live capture's useful matches were entirely outside teeth. A manual polygon can still include skin or specular enamel and cannot establish tooth identity by itself. The current dense baseline may also fail under shiny/low-texture enamel, saliva, tissue motion, pure camera rotation, weak parallax, occlusion, or inaccurate intrinsics. It does not implement full global SfM/loop closure, calibrated physical scale, per-surface photometric confidence, certified lens lock on Android, anatomical completeness or independent validation. CPU runtime and memory for full-resolution real captures remain unmeasured; the Node/Python timeouts may need adjustment from actual profiling.

The next meaningful live milestone is a reviewed video in which visible crown surfaces occupy the masks across translating, overlapping views. Acceptance should be based on inspectable source frames, three-view per-vertex support, per-tooth observed patches, reproducible geometry and eventual independent reference comparison—not on a tooth-like silhouette or a generated OBJ file.
